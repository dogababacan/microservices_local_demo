Core Idea

Microservices make system boundaries visible.

Students can inspect what each service owns, how services communicate, and why the system can be temporarily between states.

Order Service-> owns order state
Inventory Service-> owns stock reservation
Payment Service-> owns payment result
Notification Service-> owns customer messages
Analytics Service-> observes events
01

One responsibility

Each service owns one part of the checkout behavior: order lifecycle ? Lifecycle means the states an order passes through over time. In this demo an order starts as created, then becomes completed or cancelled. , stock, payment, notification, or analytics.

02

Independent runtime

Each service is a separate container. Students can stop one container and observe whether work fails, waits, or catches up later.

03

Communication choice

The gateway uses synchronous HTTP to start the order. After that, services communicate asynchronously through RabbitMQ events.

04

Eventual consistency

Services do not all update at the exact same moment. They become consistent after events are delivered and processed.

Catch-up Behavior

Stopped services behave differently depending on their position.

Notification stopped

Downstream consumer is offline

Checkout can still complete. RabbitMQ holds messages in notification_service_events_queue until Notification starts again.

docker compose stop notification-service
docker compose start notification-service
Inventory stopped

Middle consumer is offline

Order is created, then waits. The inventory_service_order_created_queue stacks messages until Inventory restarts.

docker compose stop inventory-service
docker compose start inventory-service
Order stopped

Synchronous entry dependency is offline

API Gateway cannot create the order, so it returns 502. No order.created event exists for RabbitMQ to hold.

docker compose stop order-service
docker compose start order-service

Final Takeaways

Students should leave with three architecture instincts.

Events decouple services

A publisher announces what happened. Consumers decide whether they care.

Queues make waiting visible

Stopped downstream consumers do not erase work. The queue can hold it.

Synchronous calls fail immediately

If the service needed before the first event is down, the workflow cannot begin.

The best classroom discussion is not “which tool is best,” but “which boundary creates which behavior?”
