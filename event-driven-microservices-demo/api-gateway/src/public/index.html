Async Note (Eventual Consistency)

The HTTP checkout request returns a synchronous 202 Accepted response immediately after the Order Service creates the initial record, confirming the request has been received.

However, downstream validation (such as payment processing or stock reservation) occurs asynchronously via RabbitMQ. If these downstream events fail, compensating transactions are triggered, which asynchronously cancel the order in the background, updating the Order Service record eventually.

How to read the live metrics

Ready wait
Unacked work
Consumers readers

Ready means messages are waiting in the service inbox. Unacked means a service has received messages but has not confirmed them yet. Consumers means running service instances currently reading from that queue.

One queue, many consumers

Multiple consumers on the same queue are competing readers. RabbitMQ gives each message to one of them, so this is useful for scaling more instances of the same service.

notification_service_events_queue with 2 consumers means two Notification Service instances can share notification work.
Do not put different services on one queue if both must see every event; they would split messages and miss some events.
Different services that need the same event should each have their own queue bound to the same exchange/routing key.

Manual Stopped-Service Demos

The browser observes the broker. Run container commands in your terminal; the app does not stop or start Docker services.

Stopped downstream event consumer: queue stacks and resumes later.
Stopped synchronous entry dependency: request fails before an event exists.
Not every stopped service behaves the same; it depends where it sits in the flow.

Notification stopped

Checkout still completes; the customer message waits in Notification Service's inbox.

  1. 1Stop Notification Service.
  2. 2Send a successful checkout from the left form.
  3. 3Watch notification_service_events_queue stack a ready message.
  4. 4Start Notification Service.
  5. 5Watch the ready message drain back to zero.
docker compose stop notification-service
docker compose start notification-service
docker compose logs -f notification-service

Inventory stopped

The order is accepted, but order.created waits until Inventory Service returns.

  1. 1Stop Inventory Service.
  2. 2Send a successful checkout from the left form.
  3. 3Watch inventory_service_order_created_queue stack a ready message.
  4. 4Start Inventory Service.
  5. 5Watch inventory, payment, notification, and order completion continue.
docker compose stop inventory-service
docker compose start inventory-service
docker compose logs -f inventory-service payment-service order-service notification-service

Order stopped

The first synchronous HTTP dependency is down, so checkout fails before any event is published.

  1. 1Stop Order Service.
  2. 2Send a checkout from the left form.
  3. 3Observe the API Gateway response: 502.
  4. 4Notice that RabbitMQ queues do not stack because order.created was never published.
  5. 5Start Order Service before continuing class.
docker compose stop order-service
docker compose start order-service
docker compose logs -f api-gateway order-service

Owns
System boundary validation, API endpoint definitions, and synchronous client response handling. Generates early correlation IDs.
Does NOT own
Orders database state, stock counts, credit validations, or notification distribution logs.
Why this exists
Web clients need a clean, synchronous HTTP entry point. The Gateway maps this standard HTTP input into event-driven background flows.
Port: 3001 Style: HTTP + RabbitMQ Topic Producer & Consumer Publishes: order.created, order.completed, order.cancelled Consumes: payment.completed, inventory.failed, payment.failed
Owns
The core order database records and their corresponding lifecycles (created, pending, cancelled, or completed).
Does NOT own
Inventory quantities, catalog availability, or transaction charging operations.
Why these events?
  • order.created: Announces the booking intent.
  • order.completed: Records that payment succeeded and the order lifecycle reached its happy-path outcome.
  • order.cancelled: Cancels the booking to trigger compensations when issues occur downstream.
Port: 3002 Style: RabbitMQ Topic Consumer + Producer Publishes: inventory.reserved, inventory.failed, inventory.released Consumes: order.created, inventory.release_requested
Owns
The catalog counts and physical stock reservations in memory.
Does NOT own
Customer checkout records, transactional flows, or payment confirmations.
Why these events?
  • inventory.reserved: Locks stock for payment validation.
  • inventory.failed: Rejects booking due to zero stock.
  • inventory.released: Restores stock after payment fails (compensation).
Port: 3003 Style: RabbitMQ Topic Consumer + Producer Publishes: payment.completed, payment.failed, inventory.release_requested Consumes: inventory.reserved
Owns
Payment processing logic, merchant authorization states, and simulated card results.
Does NOT own
Product catalogue details, item inventory counts, or client message channels.
Why these events?
  • payment.completed: Notifies order checkout is successful.
  • payment.failed: Reports card declined exceptions.
  • inventory.release_requested: Requests compensation stock restore since payment failed.
Port: 3004 Style: RabbitMQ Topic Consumer Only Consumes: payment.completed, payment.failed, inventory.failed

Main Role
Decouples microservices. Receives events from publishers and routes copies to queues according to configured binding patterns.
Why topic routing?
Enables precise point-to-point routing, event stream splitting, and global auditing wiretaps within a single centralized broker.
